# Experiment Digital Twin Dashboard: Architectural Blueprint & Design Guidelines

> **Purpose**: A comprehensive guide, architectural reference, and implementation blueprint for autonomous agents and engineers building interactive "Digital Twin" experiment dashboards for scientific, multi-agent, social simulation, or LLM-evaluation studies.

---

## 1. Executive Summary & Conceptual Framework

### What is an Experiment Digital Twin Dashboard?
Scientific multi-agent experiments and LLM benchmark studies are traditionally headless: executed via Python scripts, CLI tools, or batch SLURM pipelines, producing directories of nested JSON files, log dumps, and static Matplotlib figures. While reproducible for researchers who clone the repo and have appropriate compute environments, this creates high friction for external reviewers, policy stakeholders, collaborators, and broader audiences.

An **Experiment Digital Twin Dashboard** is a zero-friction, production-grade web application (typically Next.js / React / Tailwind CSS) that:
1. **Mirrors the experiment artifact filesystem**: Ingests, renders, and visualizes the exact JSON artifacts generated by the simulation engine without manual data conversion.
2. **Operates in Dual Modes**:
   - **Static Inspection Mode**: Works out of the box with zero external dependencies, rendering sample/baseline runs and disk artifacts so reviewers can inspect findings immediately.
   - **Live Simulation Mode (BYOK)**: Allows users to modify prompts, parameters, and models, enter their own API credentials (Bring-Your-Own-Key), and execute new trials directly from the browser with live visual progress streaming.
3. **Guarantees Zero-Trust Security**: Never persists user API keys to databases, disk, or remote logs.
4. **Bridges Qualitative Dialogue & Quantitative Analytics**: Provides simultaneous views of raw dialogue turns (including hidden reasoning scratchpads) and analytical metrics (geometric consensus distance, plurality, discourse quality).

```
   ┌────────────────────────────────────────────────────────┐
   │             Simulation Engine (Python / CLI)           │
   │  src/deliberation.py · src/evaluation.py · data/expXXX │
   └──────────────────────────┬─────────────────────────────┘
                              │ JSON File Parity
                              ▼
   ┌────────────────────────────────────────────────────────┐
   │             Digital Twin Dashboard (Next.js)           │
   ├──────────────────────────┬─────────────────────────────┤
   │ Static Inspection Mode   │ Live Simulation Engine      │
   │ (Baseline exp000 + Disk) │ (BYOK + In-Memory Runner)   │
   ├──────────────────────────┴─────────────────────────────┤
   │  Supabase Cloud Persistence (Optional, Read-Write RLS)  │
   └────────────────────────────────────────────────────────┘
```

## 2. Zero-Trust Security & Bring-Your-Own-Key (BYOK) Architecture

When designing a dashboard where public users or reviewers can trigger LLM runs, **never host a centralized backend with shared API keys**. This avoids unbounded billing, denial-of-service, and quota exhaustion. Instead, enforce a strict **BYOK** model.

### Key Security Principles

1. **Client-Side Storage Only**:
   - Keys must never touch the database (e.g., Supabase table columns for `api_key` must **never** exist).
   - The user can select their preferred storage strategy:
     - `sessionStorage` (cleared immediately when the browser tab closes).
     - `localStorage` (persisted locally on the user's client machine for convenience).
     - `memory` only (ephemeral state in React context/state).

2. **Ephemeral In-Memory Forwarding**:
   - When a simulation runs, the client forwards the key in the request payload or HTTP headers (`x-api-key`) to Next.js Route Handlers (`/api/run-experiment`).
   - The Route Handler uses the key strictly in-memory to initialize the OpenAI/Together/Groq client, processes the simulation turns, and returns the resulting JSON.
   - The key is garbage collected immediately upon response completion.

3. **Transparent Security Messaging in the UI**:
   - Place a dedicated API settings modal or status pill directly in the header navbar.
   - Display a verified shield icon (`ShieldCheck`) and a clear security assurance:
     > *"Zero-Trust Architecture: Your API key is stored exclusively in your browser's local memory. It is sent ephemerally over HTTPS strictly to authenticate requests and is never written to disk, saved in Supabase, or exposed to third parties."*
   - Mask the input field with `type="password"` and provide a 1-click "Purge Key from Browser" button.

4. **Database Row-Level Security (RLS)**:
   - When connecting Supabase or PostgreSQL:
     - Enable RLS on the `experiment_runs` table.
     - Public anonymous users can `SELECT` runs.
     - Writes (`INSERT`) can be allowed for new runs or scoped via authenticated roles or anon keys without compromising read integrity.
     - Never include credentials or sensitive environment variables in client-exposed bundles (`NEXT_PUBLIC_` should only expose Supabase URL and anonymous public keys).

## 3. Standard Artifact Decoupling & Directory Parity

To enable any agent or human to swap between the Python simulation CLI and the web dashboard seamlessly, structure simulation outputs into **standardized, decoupled four-file JSON bundles**:

```
data/
└── exp000/
    ├── config.json             # Declarative experiment parameters & prompts
    ├── results_control.json    # Baseline / Control condition transcript & stances
    ├── results_treatment.json  # Treatment condition transcript & scratchpads
    └── evals.json              # Analytical metrics, geometric scores, rubric totals
```

### Purpose of Each Artifact

| File | Content | UI Representation |
| :--- | :--- | :--- |
| `config.json` | Model identifiers, temperatures, seeds, turn limits, system prompts, persona profiles | **Run Configuration Sub-Tab**: Parameter cards, full system prompt viewers, copy buttons. |
| `results_control.json` | Direct dialogue turns, public statements, pre/post initial positions | **Model Outputs Sub-Tab**: Side-by-side or standard condition conversation view. |
| `results_treatment.json` | Experimental dialogue turns, private thoughts (`<private_scratchpad>`), public output | **Model Outputs Sub-Tab**: Accordion disclosure of private thoughts, highlighted reasoning blocks. |
| `evals.json` | Pre/post consensus similarities, self-shift distances, plurality (CovD), rubric judges | **Key Metrics Card & DQI Breakdown**: Prominent numbers, deltas, radar/bar criterion scores. |

## 4. Universal TypeScript Data Contracts

When adapting this dashboard to a new scientific domain (e.g., economic bargaining, legal argument generation, multi-agent voting, theorem proving), preserve the high-level schema while customizing the domain-specific fields:

```typescript
// types/experiment.ts

export interface ExperimentRun {
  id: string;                       // e.g. "exp000", "exp001"
  name: string;                     // e.g. "Baseline Dyadic Deliberation"
  description?: string;             // General study abstract
  created_at: string;               // ISO 8601 timestamp
  config: ExperimentConfig;         // Declarative configuration
  results_control: SimulationResult;// Control condition transcript
  results_treatment: SimulationResult; // Treatment condition transcript
  evals: EvaluationMetrics;         // Quantitative & qualitative metrics
}

export interface ExperimentConfig {
  deliberation_config: {
    max_turns: number;
    participants: Array<{
      id: string;
      role: string;
      stance_type: string;
      persona_prompt: string;
    }>;
    topic: string;
    rules: string[];
  };
  model_config: {
    model_assignments: Record<string, string>; // Persona -> Model ID
    model_parameters: Record<string, {
      temperature: number;
      seed?: number;
      max_tokens?: number;
    }>;
  };
  evaluation_config?: {
    judge_model?: string;
    metrics_requested?: string[];
  };
}

export interface SimulationResult {
  condition: 'Control' | 'Treatment';
  chat_history: Record<string, Array<{
    speaker: string;
    speech: string;
    scratchpad?: string; // Private reasoning trace (Treatment only)
    timestamp?: string;
  }>>;
  initial_positions?: Record<string, string>;
  final_positions?: Record<string, string>;
}

export interface EvaluationMetrics {
  Control: ConditionEval;
  Treatment: ConditionEval;
  verdict_summary?: string;
}

export interface ConditionEval {
  convergence: number;       // Final consensus similarity (0.0 to 1.0)
  self_shift: number;        // Geometric movement from baseline
  covd_pre?: number;         // Pre-deliberation plurality / volume
  covd_post?: number;        // Post-deliberation plurality / volume
  dqi?: {
    total: number;
    dimensions: Record<string, number>;
    justification?: string;
  };
}
```

## 5. UI/UX Design Guidelines & Principles

### A. Widescreen-First Responsive Layout
Scientific dashboards are data-dense. Avoid cramped containers (`max-w-4xl` or `max-w-6xl` cause truncated text and awkward line wrapping).
- **Header & Main View**: Use `max-w-[1840px] w-full px-4 sm:px-8 lg:px-12` to let tables stretch naturally across modern monitors.
- **Table Padding & Geometry**: Use generous cell padding (`px-6 py-7`) and set sensible `min-w-[...]` (e.g., `min-w-[220px]` for metric columns, `min-w-[180px]` for timestamps) to ensure headers and metrics remain uncluttered.
- **Sticky Navbar**: Keep navigation tabs and API status persistent at the top of the viewport (`sticky top-0 z-40 backdrop-blur-md`).

### B. Plaintext Labels & No Raw Python Leaks
Never expose Python variable names or raw JSON keys in user-facing UI:
- ❌ `pre_covd`, `ctrl_convergence`, `self_shift_post`
- ✅ **Baseline Pre-Deliberation**, **Standard (Control)**, **Reflective (Treatment)**, **Stance Change (Shift)**

### C. Balanced Comparative Presentation
When comparing a control and treatment condition:
- Present them with equal typographic prominence.
- Standardize all metric rows with a consistent format:
  ```
  Standard:      0.8319
  Reflective:    0.8362
  ----------------------
  Baseline Pre:  0.8482
  ```
- **Boldness**: Bolden both condition numbers and the baseline figure equally (`font-bold text-neutral-900 font-mono`).
- Avoid colored status pills in the high-level summary rows that might bias the viewer; reserve color coding for explicit deltas (`Δ +0.0043` in subtle emerald).

### D. Clear Explanatory Metric Banners
Do not assume reviewers know your metric definitions. Include a multi-card banner at the top of the directory:
1. **Experiment Mission**: What intervention is being tested (e.g., internal scratchpads vs direct generation).
2. **Consensus & Convergence**: Semantic cosine similarity measuring alignment.
3. **Plurality & Geometry (CovD)**: Covariance determinant measuring preserved perspective diversity.
4. **Discourse Quality (Rubric)**: Explaining criteria dimensions and maximum rubric scores.

### E. Multi-Subtab Expanded View
When a user clicks any run row, expand an inline panel disclosing four structured sub-tabs:
1. **Model Outputs**:
   - Provide a toggle for `Reflective (Treatment)`, `Standard (Control)`, and `Side-by-Side`.
   - Distinguish public dialogue bubbles from private thoughts (`<private_scratchpad>`) using distinct styling (amber tinted border, brain icon, italicized or monospace formatting).
2. **Run Configuration**:
   - Display active model assignment, sampling temperature, seed, and turn limit.
   - Provide full expandable cards for system prompts and persona backstories with 1-click clipboard copy buttons.
3. **Quality Breakdown (Rubric / Judge)**:
   - Breakdown of multi-dimensional scores (e.g., depth of justification, civility, interactivity) with qualitative LLM judge justifications.
4. **Directory Files (Raw JSON)**:
   - In-browser code viewer with tab selector for `config.json`, `results_control.json`, `results_treatment.json`, and `evals.json`.
   - Include both `Copy JSON` and `Download JSON` buttons.

## 6. Live Simulation Engine Implementation Pattern

When implementing the browser-based simulation runner (`LiveSimulationRunner.tsx`):

### Client Execution Loop
1. **Pre-flight Check**: Verify that `apiSettings.apiKey` is populated. If missing, prompt the user to open the BYOK settings modal.
2. **Deterministic Fallback**: If the user has not configured Supabase, run the experiment locally in browser state and save the run to React memory (`runs` array), allowing the user to download the generated 4-file bundle immediately.
3. **Step-by-Step Progress Tracking**:
   Render an animated progress card displaying the current stage:
   - `Stage 1/5: Generating Pre-Deliberation Initial Positions`
   - `Stage 2/5: Deliberating Turn 1 of 3 (Control Condition)`
   - `Stage 3/5: Deliberating Turn 1 of 3 (Treatment Condition with Scratchpads)`
   - `Stage 4/5: Extracting Post-Deliberation Positions`
   - `Stage 5/5: Computing Cosine Similarity, CovD & Running Judge Rubric`

The route handler should execute standard OpenAI-compatible completions using the user's provided API key:

## 7. Experiment Resources & Open Science Integration

A complete digital twin dashboard must include a dedicated **Experiment Resources** tab that links researchers to upstream theoretical documentation and reproducible codebases:

1. **Live Documentation (Overleaf / arXiv / Notion)**:
   - Link directly to the live document or pre-print.
   - Describe it accurately as **Live Documentation** or **Preprint**, summarizing the theoretical framework, prompt designs, and formal metric equations.
2. **Open Source Code Repository (GitHub)**:
   - Direct link to the simulation repository.
   - Outline key reproduction scripts (`python run_simulation.py`, `python evaluate.py`).
3. **Artifact Directory Architecture Map**:
   - Visual summary of `config.json`, `results_control.json`, `results_treatment.json`, and `evals.json` so external researchers understand how to parse or import data into Python/R for meta-analyses.

## 8. Implementation Checklist for New Experiment Topics

When adopting this architecture for a new scientific topic or evaluation framework, verify the following steps:

- [ ] **Dual-Mode Support**: The dashboard loads instantly with `SAMPLE_EXP000` even if no database or API key is provided.
- [ ] **BYOK Security**: Keys are stored exclusively in client memory/storage, never logged, and never written to database tables.
- [ ] **Plaintext Labels**: All metric headers and labels use readable natural language (e.g., `Baseline Pre-Deliberation`).
- [ ] **Widescreen Table**: Table containers use `max-w-[1840px]` or `w-full` with spacious `px-6 py-7` row padding.
- [ ] **Collapsible by Default**: Runs in the directory table remain collapsed upon initial load to maintain a clean overview; users expand on demand.
- [ ] **Balanced Metric Typography**: Baseline, control, and treatment numbers are boldened with equal prominence.
- [ ] **Full Config Disclosure**: The expanded view contains the complete declarative prompt templates and parameters, not just truncated fragments.
- [ ] **Exportability**: Users can download both individual JSON artifacts and complete run bundles with a single click.
- [ ] **Clean Runtime Execution**: Code builds cleanly with standard package managers (Bun / npm / pnpm) without Node version mismatches or broken polyfills.
